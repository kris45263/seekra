# 已确认的写作案例

以下三个案例在 2026-09-23 的项目协作中查阅并讨论，用户认可其参考价值。中文说明是对写法的概括，不是原文译本；借鉴范围限于指出的段落，不代表认可整个项目的所有文档。链接指向可变化的分支，后续引用具体事实时应重新核对原文。

## 案例一：rust-analyzer 先建立整体认识，再解释概念

来源：[Architecture — Bird's Eye View](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md#birds-eye-view)。

该段先介绍系统接收源代码、生成语义模型，再解释输入包含哪些内容，以及语义模型如何表达模块、函数、类型和引用关系，之后才介绍输入变化后的更新。

值得借鉴的是概念出现的顺序：读者先知道系统的工作，再理解完成这项工作所需的术语。语义模型这样的名称紧接着得到解释，读者有了具体认识后，再阅读更新机制。

适用范围：介绍系统、子模块或读者尚不熟悉的概念。面向熟悉接口的读者查询参数时，可以直接给参数说明，不必每次重新介绍系统。

## 案例二：rust-analyzer 从实际场景解释取消

来源：[Architecture — Cancellation](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md#cancellation)。

该段从编辑器正在计算高亮、用户又输入文字的场景切入，解释旧结果为何需要取消，再说明检测变化和传递取消的机制。

值得借鉴的是把条件、原因和处理过程连起来。输入变化使旧结果失去用途，这个场景解释了为什么需要取消；后面的机制说明则回答系统如何发现变化、如何结束旧计算。

适用范围：读者需要理解某个机制为何存在以及何时发生。借鉴的是从场景展开解释的方式，具体实现仍由所描述的系统决定。

## 案例三：Redis 把数据结构放进执行过程

来源：[Redis 7.2 README — Redis internals](https://github.com/redis/redis/blob/7.2/README.md#redis-internals)，重点阅读 `server.h`、`server.c` 和 `networking.c` 小节。

说明先介绍服务器和客户端保存的数据，再介绍启动、读取请求和执行命令。解释客户端缓冲区时，继续交代请求如何进入、如何被解析，以及回复如何发送。

值得借鉴的是把静态结构和使用过程连接起来。缓冲区的含义通过请求写入、解析和回复发送这些动作变得具体，读者能够理解数据结构怎样参与程序运行。

适用范围：架构说明、源码导读和状态管理说明。介绍范围按读者需要选择，无需逐文件覆盖所有代码；数据组织方式以所描述的系统为准。
