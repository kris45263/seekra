# 写作与文档修改

文档应当让目标读者通过文字本身理解系统，不必靠猜测补齐对象、条件和因果关系。

## 从读者需要理解的内容出发

写作前明确文档用途、目标读者和读者已有的背景。架构说明可以假定读者理解基本 Python 和模型工具调用，但应解释 Seekra 特有的概念；用户使用说明则应围绕用户需要完成的操作组织。

首次使用本技能时阅读 [已确认的写作案例](references/cases.md)。后续遇到组织或表达上的疑问，回看相关案例，判断它的解释方式是否适用于当前内容。

- 先建立整体认识，再解释必要概念和具体机制。术语首次出现时，说明它在本项目中指什么；保留有助于定位源码的名称。
- 描述行为时交代谁在什么条件下做什么，以及产生什么结果。省略的主语、对象或条件若可能改变理解，就补全。
- 解释设计时把触发场景、需要解决的问题和处理方式连起来，让读者知道为什么采用这个机制。
- 结合数据流和执行过程解释模块、字段及函数，说明谁产生数据、谁保存、谁消费，避免只有职责名称或字段清单。
- 每个段落围绕一个需要解释的问题展开。新概念依赖前文时，先提供必要前提；表格适合并列比较，步骤适合有先后顺序的过程。

这些是判断依据，不要求每节套同一个结构、每段都补一个例子，也不以长短或术语数量衡量清晰程度。能够精确表达条件的技术术语可以使用。

## 修改已有文档

先检查现有内容的前提、用途和位置，再决定局部修改还是重组。文档应说明当前用法、模块职责与仍然有效的设计理由；实现或适用前提改变时同步更新。

一次局部修改也要重新阅读所在的完整段落和相关章节，确认对象、条件、因果和指代仍然连贯。不要只在旧句子后追加一句纠正说明，留下相互牵制的表述。历史兼容规则和证据边界仍可能有当前用途，应判断后处理。

按影响范围核对相关源码、模型指令、文档和测试。区分代码已经实现的行为、提示词提出的要求、实验观察和未验证判断，不能把“希望模型这样做”写成程序保证。

## 内容放在哪里

|位置|长期用途|
|---|---|
|`README.md`|安装、配置、使用和用户可见限制|
|`docs/architecture.md`|模块职责、关键数据流、重要接口和设计理由；避免逐项复述源码|
|`docs/development.md`|开发环境、命令和修改入口|
|`docs/validation.md`|可复用的验证方法与证据边界|
|`docs/research-findings.md`|仍有参考价值的研究结论|
|`evals/`|原始精选证据与可复用评估，按需查阅|
|`docs/skills/`|项目协作方法及经过确认的案例依据|

模型行为指导、接口契约和维护规则分别放在相应位置，合并重复说明。新增文档应有现有类别之外的长期维护用途，不按每次任务新增分析、计划、排查或验收报告。用户明确要求的交付文档按要求处理。

## 从读者角度检查结果

完成后按正常阅读顺序通读修改范围，重点判断：读者能否知道对象是什么、条件何时成立、前后步骤怎样连接，以及结论凭什么成立。再检查链接、格式和必要的源码对应关系。简单文案改动通常检查文档结果即可，验证范围按 [测试修改](../project-testing/SKILL.md) 判断。

读者指出“我把这句话理解成了另一件事”时，把它作为实际反馈，定位缺失的对象、条件、指代或上下文。先解决产生误解的表达，再决定是否需要补充新的写作原则。
