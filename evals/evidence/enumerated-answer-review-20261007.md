# 完整字段枚举复核：未达到集成条件

日期：2026-10-07。生产代码及默认流程未改动。

## 实验问题

程序列出完整终稿里所有模型文本字段，能否让一次同模型复核修正已知错误，同时保留正确内容？检查范围包含判断、条件、建议、未知问题与影响、模型标题；原文和 evidence 不允许修改。

复核者对每个路径必须返回 keep、revise 或 uncertain，并给出理由。允许指定文本替换、新增未知及明确的建议关联变更；程序校验覆盖范围，再通过现有编译器检查修订稿。没有反复自审或隐式重写。

## 固定材料与边界

- 两份来自既有真实运行的完整错误答复：周期联网和部署检查通知。
- 一份既有局部阅读答复，以及一份人工核对过的完整正确答复，作为正向对照。后者明确允许保守的提前安排，并区分调查动作与条件式方案。
- 每份独立复核两次，共8次模型请求；deepseek-flash，reasoning high，输出预算8192。
- 输入包含用户原问题、固定虚构原文、完整草稿和程序枚举的字段路径。判准和样本角色未发送给模型。
- 这是固定答复的冷启动复核试验，没有重新搜索、Tavily 调用、长期研究或恢复测试。

## 原文、断言和复核理由

### 离线验证

原文只规定连续离线30天后需要再次在线验证。原稿却断言“每28天联网一次的时间安排能满足文档的验证节奏”，没有确认具体联网、验证和计时重置机制。

复核者对此字段返回 keep，理由为：

> 每28天联网使连续离线不达30天触发点，满足验证节奏的推论成立。

修订后的该断言与原稿完全相同。把所有字段列出来，仍未使复核者识别这项无充分依据的可行性承诺。

### 检查后通知

原文为“When the review is complete, notify the service owner.”。原稿在判断的条件中写出“应随第7天的检查完成而立即通知，而非拖到第10天”。按既定判准，明确标注的尽早通知建议可以保留，但不能把提前或立即要求作为原文明示截止。

第一次复核保留该条件，理由为：

> 以检查完成为前提推导通知时点，与来源条款一致，未引入额外要求。

第二次也保留相关通知建议，理由为：

> 检查完成后立即通知所有者，与源文通知条款一致。

本批显示复核者认可了原稿的时点归因。这里的判定不以出现“立即”一词就拒绝建议，而是核对它是否被当成来源规定。

## 成本与失败记录

8次请求报告输入 token 18,074、输出 token 34,992；输出包含服务报告的 reasoning token。请求耗时合计 158.7 秒，属于本批轨迹，不代表稳定成本。

一次 StreamProtocolError 没有返回完整可用复核，不计作语义通过或漏判。该请求报告了8193个输出 token，配置预算为8192；实验器没有保留具体协议错误文本，不能只凭这个数值确定失败细节。其请求和用量没有被删除，也没有通过额外重跑掩盖。

## 取舍

前置验收未通过：正确对照得到保留，但现有错误答复的3次完整复核均未修正目标错误。因此没有进入未见场景测试，没有接入默认终稿流程，也没有追加多轮同模型复核。

在本批样本中，完整枚举解决了程序层面的检查范围覆盖，却没有改变模型对原文与断言之间关系的错误判断。这只否定当前模型、输入方式与单轮复核方案在这些样本上的集成依据，不证明所有复核方法都无效。
